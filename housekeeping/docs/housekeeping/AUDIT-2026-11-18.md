# HOSIS Housekeeping: Panel Audit, November 18, 2026

A strict review of the whole Housekeeping subsystem (backend, frontend,
database and documentation), done the way a defense panel would read it.
Every finding below was fixed in this round unless it is marked
**Not fixed**, with the reason.

**Out of scope here:** room status paging, lost & found security, QR codes
and report downloads. The professor flagged those separately and they were
handled in their own round of changes.

## Severity scale

| Rating | Meaning |
| ------ | ------- |
| **Critical** | Breaks a business rule or exposes data in normal use |
| **High** | A rule can be bypassed, or data can become wrong, by a direct API call or two people acting at once |
| **Medium** | Leaks information, wrong behavior in edge cases, or misleading screens |
| **Low** | Quality, consistency, accessibility, or maintainability |

## 1. Business rules and data

### H-1 (High) A room could pass inspection without its checklist
**Where:** `backend/src/modules/housekeeping/inspections.routes.js`
**Problem:** The Inspection page only enables "Pass" when all five checklist
items are ticked, but the API accepted `result: PASSED` with no checklist, a
partial one, or any JSON at all (stored as-is, up to the 3 MB body limit). A
panelist with Postman could approve a room nobody checked.
**Fix:** The checklist must be the five known items (`bed`, `bathroom`,
`amenities`, `floors`, `fixtures`) with true/false values; unknown keys,
non-boolean values and arrays get a 400. A pass needs all five true. Only the
clean, known shape is saved.

### H-2 (High) Guest request stock could be approved for one item and saved as another
**Where:** `guestRequests.routes.js` (PATCH and complete)
**Problem:** Editing a request read the row, checked "stock already
approved?", then updated it, with no lock. An approval at the same moment
could land in between, so inventory was reduced for one item and amount while
the request ended up showing another. Completing had the same gap with the
"approve stock first" rule. A missing request also returned 409 instead of 404.
**Fix:** Both run in a transaction on a locked row (`SELECT ... FOR UPDATE`),
the same way approval already did. A missing request now returns 404.

### H-3 (High) Two open cleaning tasks could be created for one room
**Where:** `tasks.routes.js` (POST)
**Problem:** "One open task per room" was checked with a plain SELECT. Two
supervisors creating a task for the same room at the same moment both passed.
**Fix:** Creating a task locks the room row first, so the second request waits
and then sees the first task.

### M-1 (Medium) Lists grew without limit
**Where:** `GET /tasks?status=INSPECTED`, `GET /guest-requests?view=all`,
`GET /maintenance?view=all`
**Problem:** Each returned every row since the system started. After a few
months of real use the Inspection, Guest Requests and Maintenance pages would
load thousands of rows every 30 seconds.
**Fix:** Passed inspections: last 30 days. Guest requests: open ones plus
those completed in the last 30 days. Maintenance: open ones plus the last 90
days. The pages say so. Older records stay in the database and in My Record.

### M-2 (Medium) Past shifts could be deleted, and there was no way to remove a shift on screen
**Where:** `schedules.routes.js` (DELETE), `SchedulesPage.jsx`
**Problem:** The API deleted any shift, including ones that already happened
(they count as "shifts worked" on My Record and in work reports). At the same
time the Schedules page had no remove button, so a supervisor who made a
mistake could not undo it.
**Fix:** Past shifts cannot be removed (409). Future shifts get a
"Remove shift" button with a confirm step.

### L-1 (Low) Invalid calendar dates on the schedule list
`GET /schedules?date=2026-02-31` passed the format check and reached
PostgreSQL. It now uses the same real-date check as the other date fields (400).

### L-2 (Low) Room condition details were silently cut off
`POST /room-reports` cut the message at 255 characters without telling the
user. Details over 200 characters are now refused with a clear message (the
page already limits the box to 200).

### L-3 (Low) Stock count reason could be blank spaces
An ADJUST movement accepted `"   "` as its reason. It now has to contain text.

## 2. Security

### M-3 (Medium) Sign-in timing showed which accounts exist
**Where:** `auth.routes.js` (`/login`)
**Problem:** For an unknown name the server answered at once; for a real name
it ran bcrypt (about 70 ms). Timing the answers tells an attacker which
usernames and emails are real.
**Fix:** An unknown name is compared against a dummy bcrypt hash, so both
cases take the same time.

### M-4 (Medium) "Forgot password?" lockout showed which accounts exist
**Problem:** Only unknown names were counted toward the lockout. After five
tries an unknown name got "Too many attempts" while a real one never did,
which again reveals real accounts. Real names could also be sent without any
limit.
**Fix:** Forgot-password has its own limit (5 per name and address per 15
minutes), counted the same for every name. A unique index now guarantees at
most one waiting request per person.

### M-5 (Medium) Database details sent to the browser
**Where:** `middleware/errorHandler.js`
**Problem:** A failed CHECK constraint returned `Invalid value: Failing row
contains (...)`, exposing table columns and other values from the row.
**Fix:** The browser gets a plain message; the detail is only written to the
server log.

### M-6 (Medium) Search input used as a pattern
**Where:** tasks, guest requests, inventory searches
**Problem:** `%` and `_` typed by a user were treated as wildcards, and the
search text had no length limit.
**Fix:** A shared `likePattern()` helper escapes them and refuses searches
over 100 characters.

### L-4 (Low) Tokens without a password version were accepted
`authenticate` only checked the password version when the token had one. A
token signed without it would never be signed out by a password change. All
tokens must now carry it.

### L-5 (Low) No security headers
Responses now carry `X-Content-Type-Options: nosniff`, `X-Frame-Options:
DENY`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, and the
`X-Powered-By: Express` header is removed.

### L-6 (Low) Login failure table never cleaned
Every mistyped name left a row in `hk_login_failures` forever. Rows older than
a day are now deleted.

## 3. Frontend UX and accessibility

### M-7 (Medium) Network or server errors showed raw JavaScript messages
**Where:** `api.js`
**Problem:** With the backend down, users saw "Failed to fetch" or
"Unexpected token '<'" (the proxy's HTML error page parsed as JSON).
**Fix:** These now read "Cannot reach the server..." and "The server had a
problem...".

### M-8 (Medium) Notification badge missed new alerts
**Where:** `NotificationBell.jsx`
**Problem:** "New" was the number of alerts minus the number seen. If one
alert cleared and a different one arrived, the badge showed nothing new.
**Fix:** Alerts are remembered by what they are, not how many there were.

### M-9 (Medium) Pop-up windows trapped screen reader and keyboard users outside
**Where:** `Modal.jsx`
**Problem:** Opening a pop-up left focus on the page behind it; Tab moved
through hidden page content; closing lost the user's place.
**Fix:** Focus moves into the pop-up, Tab stays inside it, Escape closes it,
and focus returns to the button that opened it.

### M-10 (Medium) Maintenance form refused occupied rooms only after submit
**Where:** `MaintenancePage.jsx`
**Problem:** "Set room OUT OF ORDER" is ticked by default. For an occupied or
reserved room the server refuses that, so the report failed after the user
filled everything in. The Report Room page already handled this; Maintenance
did not.
**Fix:** For occupied or reserved rooms the option turns off with an
explanation, and the report still goes to Engineering.

### L-7 (Low) "Access denied" screen had no way out
A stored session from a non-Housekeeping account showed "Access denied" with
no sign-out button. One was added.

### L-8 (Low) End-session warning showed the whole department's work to housekeepers
A housekeeper was warned about every open task in the hotel. They now see
only their own unfinished rooms; leads still see the department totals.

### L-9 (Low) Sign-in screen wording
The field said "Staff username" but the placeholder and errors said email.
It is now "Email or username". The Access Denied box always said
"Unauthorized account" even when the account was simply inactive; it now
shows the server's actual reason.

### L-10 (Low) Staff Accounts offered a reset that always failed
Other supervisors were listed with a "Reset password" button the API always
refuses. They are no longer listed (except for an admin).

### L-11 (Low) Text boxes allowed more than the database holds
Task notes, inspection remarks, schedule area and notes, maintenance
description and completion notes had no length limit, so long text failed
only on save. Each box now stops at its column size, and blank-space-only
input no longer enables Save.

### L-12 (Low) Misleading messages and labels
* "Room is now CLEAN" / "the room is DIRTY" were shown even for occupied
  guest rooms, which keep their status. The messages now match.
* Inspection said "Oldest first" but was sorted by priority; it is now sorted
  by when cleaning finished.
* Guest Requests' card said "Open requests" while also listing completed
  ones; it now defaults to open and in-progress requests with a status choice.
* Its "Assign a staff member before the request can be completed" note was
  not a real rule (the API lets whoever completes it take it); reworded.
* The top bar said "Shared session active", which meant nothing; removed.
* Page titles "LOST & FOUND" and "Guest Request" did not match the menu.

### L-13 (Low) Search boxes and table rows for keyboard and screen readers
Search boxes had only a placeholder (no label); they now have one. Selectable
table rows reacted to Enter only; Space works too, and the selected row is
announced.

### L-14 (Low) Schedules search did nothing
The staff schedule filtered on a `search` prop that was always empty. It now
has its own search box.

## 4. Documentation and dead code

### M-11 (Medium) README described a rule the code does not have
The README said Housekeeping can mark an **OCCUPIED** room DIRTY by hand.
The code (correctly) leaves that to Front Office's check-out. A panelist
comparing the two would call this an inconsistency. Fixed, and the new rules
from this audit (checklist, forgot-password limit, list history, removing
shifts) were added to the Business rules section.

### L-15 (Low) Unused API function
`api.notifications()` was never called by the frontend; removed.

### L-16 (Low) Duplicated constant
`FRONT_OFFICE_HELD` was defined twice (room status rules and maintenance);
maintenance now imports the shared one.

### L-17 (Low) Missing indexes
Added indexes for `hk_inspections.task_id`, `hk_cleaning_tasks.room_id` and
`hk_guest_requests.room_id`, which every inspection list, room page and
personal record uses.

## Not fixed (and why)

| Finding | Rating | Why it stays |
| ------- | ------ | ------------ |
| Session token is kept in browser storage, so a cross-site script could read it | Medium | Moving to httpOnly cookies changes the login contract the combined HOSIS app shell relies on (`HousekeepingApp session` prop). React escapes all output and there is no `dangerouslySetInnerHTML`, which keeps the risk low. Recommend for the integrated version. |
| `GET /guests` lists every guest name to all Housekeeping staff | Medium | The guest table has no link to rooms or stays in this subsystem, so there is no way to show only the guest in a given room. Front Office owns that data; it belongs in the integration work. |
| Any housekeeper can release a repaired room from Maintenance | Low | Matches the flowchart ("Housekeeping releases"); the room still goes DIRTY then through cleaning and inspection, so nothing unsafe is sold. |
| Sign-in lockout is per address and name, so many addresses can still guess | Low | A full rate limiter needs a shared store (e.g. Redis); out of scope for the class deployment. |
| The 3 MB request size limit applies to every route | Low | It exists for lost & found photos, which another round of changes owns. |
| `search=""` prop still passed to every page | Low | Room Status and Lost & Found still read it; those files belong to the other round of changes. |
| `LostFoundPage.jsx` lint warning (missing hook dependency) | Low | Same reason as above. |
